# Weight Bet 业务规则与边界

本文档记录当前代码实现已经确认的业务规则。接口、Android、iOS 的页面行为应以这些规则为准。

## 1. 计划状态流

```text
PENDING
  ├─ 参与者接受邀请 → WAITING_DOUBLE_CHECK
  ├─ 创建者撤销/取消 → CANCELLED
  ├─ 被邀请人拒绝 → REJECTED
  └─ 未生效且到期 → EXPIRED

WAITING_DOUBLE_CHECK
  ├─ 创建者确认目标 → ACTIVE
  ├─ 创建者放弃 → CANCELLED
  ├─ 拒绝 → REJECTED
  └─ 未生效且到期 → EXPIRED

ACTIVE
  ├─ 到期 → 保持 ACTIVE，进入结算扫描
  ├─ 结算成功 → COMPLETED
  └─ 任一参与者放弃 → CANCELLED

COMPLETED / CANCELLED / REJECTED / EXPIRED
  └─ 终态，不允许再次进入其他业务状态
```

`PENDING -> ACTIVE` 仍被状态管理器保留，用于兼容历史客户端；新流程必须经过 `WAITING_DOUBLE_CHECK`。

## 2. 资金规则

- 创建计划时，创建者冻结 `bet_amount`。
- 参与者接受计划时，参与者冻结同额 `bet_amount`。
- `bet_amount` 必须大于等于 `0.01`。
- 充值和提现金额也必须大于等于 `0.01`；余额变更必须同步写入交易流水。
- iOS 充值与提现必须读取当前用户已绑定的 `payment_method_id`；未绑定时展示明确提示，不使用测试卡号或虚拟银行卡。
- 真实充值走 `/api/payments/charge/intent`，客户端通过 Stripe PaymentSheet 收集支付方式，后端只接收 PaymentIntent 结果并由 Webhook 入账；页面校验不能替代接口校验。
- 提现仍需绑定提现方式；Stripe 模式在 Connect/Payout 完成前会拒绝提现请求，不能把本地余额扣减当作真实出款。
- 当前演示环境的绑定页面只提交脱敏支付方式标识（卡号后四位）；生产环境需要接入支付网关 tokenization，禁止提交卡号和 CVV。
- 冻结、解冻、转账和结算释放均需要余额行锁。
- 同一用户、同一计划只能产生一笔有效冻结。
- 同一冻结流水只能解冻一次。
- 结算释放具有幂等性，重复结算不能重复增加可用余额。
- 结算入账金额不能超过双方资金池总额。
- 双方都达成目标：双方各取回本金，不收手续费。
- 一方达成目标：达成方获得双方资金池，不收手续费。
- 双方都未达成目标：扣除 10% 平台手续费后平分剩余金额。

## 3. 到期与结算边界

`ACTIVE` 到期计划不能直接标记为 `EXPIRED`。原因是冻结资金仍需通过结算流程释放。

正确流程为：

1. 扫描 `ACTIVE` 且 `end_date <= now` 的计划。
2. 进入双方结算选择或定时结算流程。
3. 结算成功后写入唯一结算记录，并将计划改为 `COMPLETED`。
4. 结算失败时回滚余额、流水和计划状态。

只有尚未生效且 `end_date <= now` 的 `PENDING` 或 `WAITING_DOUBLE_CHECK` 计划可以进入 `EXPIRED`；有效期内的计划不能通过状态接口提前过期。

## 4. 权限边界

- 创建者可以确认参与者目标并使计划生效。
- 创建者可以撤销未生效计划。
- `PENDING` 和 `WAITING_DOUBLE_CHECK` 可以取消；`revoke` 只适用于尚未被接受的 `PENDING` 计划。
- 参与者可以接受或拒绝邀请。
- 指定邀请只能由邀请记录中的 `invitee_id` 接受；没有邀请记录的计划才按开放计划处理。
- 一个计划只允许一条邀请记录；重复邀请返回 `409`，更换被邀请人需要走取消并重新创建计划的流程。
- 结算状态同时返回双方提交标记和 `current_user_submitted`；客户端只能依据当前用户标记决定是否允许再次提交。
- `ACTIVE` 状态下创建者和参与者都可以放弃计划。
- 放弃计划接口必须显式提交 `confirmation=true`；缺少确认或提交 `false` 时不得改变状态、资金或邀请记录。
- 非计划参与者不能接受、确认、放弃或提交结算选择。
- 计划详情只对创建者、已接受参与者和当前有效邀请对象开放；未登录或无关用户不能通过 `plan_id` 查询。
- 打卡历史只对计划双方开放；查看对方时只返回已审核记录，本人可以看到自己的待审核记录。
- 公开减重榜和连续打卡榜只统计 `APPROVED` 打卡，待审核或已拒绝记录不参与排名。
- 只有双方结算选择匹配后，普通结算才允许执行；不匹配时进入仲裁或等待流程。
- 结算和每日提醒的调度器入口必须携带 `X-Scheduler-Key`；未配置密钥时接口不可执行。
- 通知公开发送接口当前仅允许用户操作自己的 `user_id`；系统通知由服务层内部调用，普通登录身份不能借接口向任意用户发送通知。

## 5. 结算选择轮次

- 只有 `ACTIVE` 且已到期、已经形成双方参与关系的计划可以提交结算选择；服务层会再次校验，不能依赖页面隐藏按钮实现限制。
- 计划创建时 `settlement_round = 1`。
- 双方选择不匹配时，匹配服务将计划轮次原子推进到下一轮；下一次提交必须使用持久化后的轮次。
- 一方提交后超时，超时服务推进轮次；第三轮仍无法匹配时进入仲裁。
- 轮次状态保存在计划记录中，不能仅通过“最新一条选择记录”推断，避免并发请求或重试造成重复使用旧轮次。
- 同一计划、同一用户、同一轮次只能有一条选择记录，数据库唯一约束与服务层重复检查同时生效。

## 6. 幂等与并发边界

- 计划行在关键状态转换时使用 `FOR UPDATE`。
- 余额行在资金变更时使用 `FOR UPDATE`。
- 结算记录按 `plan_id` 唯一，一个计划只能有一条普通结算记录。
- 退款流水按用户和结算关联 ID 建立唯一约束。
- 同一结算中，每位参与者最多提交一条争议记录；重复请求由服务层和数据库唯一约束共同拦截。
- 资金操作重试时必须返回已有流水，不能再次改变余额。

## 7. 当前验证范围

- 核心资金、支付、结算和计划测试已通过。
- Android XML、Python 编译和差异检查已通过。
- iOS 需要 macOS/Xcode 才能完成真实编译和逐页截图验证。
- 完整后端测试仍需要在安装完整 requirements 的干净环境中执行。

## 8. 后台管理边界

- 后台入口为 `/admin/`，与移动端共用同一个 FastAPI 服务和登录接口。
- 普通注册用户默认角色为 `user`；只有数据库角色为 `admin` 的用户可以访问 `/api/admin/*`。
- 首个管理员必须由部署人员执行 `python scripts/create_admin.py <email>` 提升，不能通过注册接口自助获得管理员权限。
- 后台可以查看用户、计划、待审核打卡和结算争议，并记录打卡审核结果或争议处理结果。
- 后台不直接修改用户余额、不绕过结算服务发放资金；资金变化仍只能通过资金服务和结算流程产生。
- 后台争议处理的 `resolved_by` 和 `resolved_at` 必须记录实际管理员，普通用户接口不能伪造。
